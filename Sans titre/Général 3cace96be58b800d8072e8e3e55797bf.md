## 2. Swimlane — Charlie Connect

Charlie Connect est une application de monitoring BLE/beacons, distincte de Charlie Gestion Mobile. Elle fonctionne en continu, détecte les entrées/sorties de régions BLE, scanne les capteurs, acquiert une localisation et remonte des inventaires horodatés. Les endpoints sont : `/api/v2/monitoringMessages` et `/api/monitoring`, ce dernier avec signature RSA SHA-256 via `X-Signature`.

### Règle de classification

Pour Charlie Connect, les codes de traitements sont :

| Cas | Code |
| --- | --- |
| Charlie Connect classique | `330` |
| Charlie Connect avec un capteur zone | `310` |
| Charlie Connect communautaire | `331` |

Ces codes viennent de la convention où `3XX` représente Connect, et les variantes `310`, `330`, `331` sont explicitement listées.

---

## 3. Swimlane — Charlie Gestion Mobile

Charlie Gestion Mobile est l’exception structurante : **le traitement ne passe pas par Mongo en première intention**. L’application est en Flutter, connectée exclusivement en API REST, avec fonctionnement offline-first. Les événements terrain peuvent être stockés localement puis rejoués en cas d’échec réseau.

### Règle de classification

| Cas mobile | Code |
| --- | --- |
| Téléphone avec capteur zone | `210` |
| Téléphone non envoyé avec capteur zone | `211` |
| Inventaire téléphone avec capteurs ou ≥ 2 capteurs zone | `220` |
| QR Code | `221` |
| Téléphone non envoyé sans capteur zone, traité comme Connect | `230` |

La convention documentaire indique que `2XX` correspond au téléphone, avec ces sous-codes.

---

## 4. Swimlane — Ercogener via MQTT / VerneMQ

Pour Ercogener, la source arrive en MQTT via VerneMQ. Les flux IoT passent par VerneMQ, qui authentifie via Charlie_interne et route les messages vers les bons workloads.

Ercogener GC81 / GC06 est associé à `manufacturer = ela` et `integrator = charlie`.

### Règle de classification tracker

| Cas tracker | Code |
| --- | --- |
| Tracker associé à une zone, sans BLE / sans CP | `131` |
| Tracker associé à un matériel, sans BLE / sans CP | `132` |
| Zone avec tracker qui fait une trame BLE | `110` |
| Zone avec un seul capteur zone détecté par tracker | `111` |
| Tracker avec scan BLE / trame CP sans capteur zone ou cas ambigu | `130` |

Ces codes sont explicitement listés dans le traitement inventaire et le tableau des cas.

---

## 5. Swimlane — Teltonika et Digital Matter via Flespi Panel

Pour Teltonika et Digital Matter, la source utilisateur indique une arrivée via **Flespi Panel** puis communication des inventaires via endpoint. Les métadonnées Mongo attendues : Teltonika GC234 avec `manufacturer = teltonika`, `integrator = charlieflespi` ou `Connectic`; Digital Matter TCOY3G est également documenté avec `manufacturer = teltonika`, `integrator = Connectic`.

---

## 6. Swimlane — Abeeway via endpoint

Abeeway arrive via endpoint selon la demande. Le document général indique `manufacturer = abeeway`, `integrator = charlie`.

Le traitement métier reste le même que les trackers : Mongo d’abord, puis normalisation, puis inventaire SQL.

---

## 7. Gestion des inventaires retardés

C’est un sujet critique pour la robustesse métier. Un inventaire peut être décalé quand un tracker n’a plus de batterie, n’a pas de réseau, ou quand un inventaire mobile est réalisé sans réseau. Elle distingue deux cas : si la date de détection et la dernière position sont postérieures à la date d’inventaire, on ne met pas à jour l’état courant; si la date de détection est postérieure mais la dernière position enregistrée est antérieure, certains champs peuvent être mis à jour, notamment mouvement, statut et site via geofencing.

---
