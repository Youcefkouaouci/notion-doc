## Principe général

Principaux travaux de découpage :

- Dans chaque modèle, une méthode dédiée `headers()` , qui permettra de récupérer les en-têtes souhaitées et traduites (partie gauche), liées aux valeurs des données (partie droite).
    
    Exemple partiel de `Material` :
    
    ```php
    return [
    	__('messages.internalReference') => 'internalReference',
    	__('messages.buyingDate')        => 'buyingDate',
    ];
    ```
    
- Un contrôleur permettant d’avoir un point d’accès sécurisée et de gérer la validation des champs, puis faisant appel au job si tout est validé
- Un Job `GenericExport` permettant de faire les appels concrets aux méthodes d’export :
    - Selon le modèle donné en paramètre, soit :
        - Une fonction globale et générique d’export (`export`, contenue dans `ExportService`), pour tous les modèles relationnels, contenant les méthodes de :
            - Filtrage colonnes : afficher certaines colonnes uniquement dans l’export
            Le nom des colonnes sera pris depuis le stockage local (côté client), où elles sont stockées, notamment selon la langue utilisateur. Structure :
            
            ```json
            "columns": ["internalReference", "buyingDate", "comment"],
            ```
            
            - Génération du fichier et écriture des en-têtes
            - Appel à la méthode générique de filtre et ajout des compteurs de champs relationnels (nombre de matériels, sites et ou zones)
            - Appel aux `ResourceCollection` pour récupérer les données correctement formatées
            - Ecriture des données ligne par ligne
            - Génération d’un fichier temporaire
            - Retour de données sous forme chemin vers le fichier nouvellement généré
        - Une fonction d’export des inventaires (voir ci-dessous)
    - Un envoi de mail dédié à l’utilisateur avec en pièce jointe le document généré
- Un Trait `Searchable` pour gérer le filtrage divers :
    - Filtre par mot clé (inclus dans au moins un des champs, dont les noms correspondant aux clés étrangères)
    - Filtres par champ (ex: `typeId=10`)
    - Filtre selon les filiales actuellement visibles par l’utilisateur

## Inventaires

L’export de l’inventaire est particulier en plusieurs points :

- Sa structure de table est unique et implémentée sur du NoSQL ;
- Les données peuvent être très nombreuses, dépendant du nombre d’antennes et de la fréquence d’envoi ;
- Il fonctionne comme un historique, contenant la liste de tous les équipements qui ont été détectés à un instant T ;
- Il dispose de filtres personnalisés :
    
    ```json
    "filters": {
    	{
    		"before": "2025-01-06 11:00:00",
    		"after": "2025-01-06 09:00:00",
    		"typeOfInventory": 110
    	}
    }
    ```
    
    Note : La date dans le champ `before` doit être plus grande que celle dans ~~after~~, si ces 2 filtres sont renseignées.
    

Pour cela, il dispose d’une méthode spécifique `exportInventories` dans l’`ExportService`.

# Etat de l’art (V2)

## Structure de fichiers

Sur la V2, un `ExportController` permet d’effectuer les exports via API. Le point d’accès s’effectue via une requête POST, en utilisant `/export` dans la requête. Il est nécessaire d’être authentifié pour effectuer un export.

Ses règles sont les suivantes :

```php
$rules = [
    'limit'           => 'integer',
    'fileType'        => 'required|in:xlsx,csv',
    'fileName'        => 'required|string'
];
$request->validate($rules);
```

3 exports sont possibles : pour les **matériels, zones et inventaires**. Pour chaque modèle, une classe spécifique existe. Toutes étendent la classe abstraite `Export`.

L’export, dans la méthode `getRequest`, prend en compte 3 paramètres : l’utilisateur, les paramètres données, et le modèle qu’on souhaite exporter. Les paramètres contiennent : la limite, le nom de fichier, le type de fichier, mais aussi les divers champs que l’ont souhaite exportés (dynamiques donc).

Dans chacune, on retrouve des méthodes communes étendues : `buildColumns`, `setTableRecordsCount`, `getDataChunksToExport`, et `getHeaders`.

⚠️

`ZonesExport` contient une extension spécifique `spreadSheetTransformations` pour **forcer le numéro de tracker à être considéré comme une chaîne de caractères** :

$spreadsheet->getActiveSheet()->setCellValueExplicit("{$column}{$row}", $cellValue, DataType::TYPE_STRING);

## Code d’export et détail de la méthode

### Le code

Le code principal d’export se trouve donc dans la classe `Export`, en particulier dans la méthode `export` :

```php
public function export()
    {
        // Fetch records from database
        $chunks = $this->getDataChunksToExport();

        // Create a new PhpSpreadsheet instance
        $spreadsheet = new Spreadsheet();

        // Set column headers
        $headers = $this->getHeaders();
        $spreadsheet->getActiveSheet()->fromArray($headers, null, 'A1');

        // Start row count
        $rowCount = 2;

        // Add data to the spreadsheet for each chunk
        foreach ($chunks as $chunk) {
            foreach ($chunk as $row) {
                $this->buildColumns($spreadsheet, $row, $rowCount);
                $rowCount++;
            }
        }

        $this->spreadsheetTransformations($spreadsheet);

        // Create the writer corresponding to the filetype
        if (ExportController::XLSX_FORMAT == $this->fileType) {
            $writer = new Xlsx($spreadsheet);
            $fileExtension = '.xlsx';
        } else {
            $writer =  new Csv($spreadsheet);
            $fileExtension = '.csv';
        }

        // Save the spreadsheet to a file
        $filename = rawurlencode($this->fileName) . $fileExtension;
        $writer->save($filename);

        return $filename;
    }
```

### Etapes

1. Chargement des enregistrements depuis la BDD
2. Création de la feuille de calcul, définition des headers, mise en place du pointeur d’écriture
3. Pour chaque sous-ensemble de données (chunk), on ajoute la ligne de donnée
4. Formatage des données
5. Création du type de fichier selon format souhaité
6. Encodage du chemin et sauvegarde du fichier
